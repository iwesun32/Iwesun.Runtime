# IPv6 精确出口网卡身份修复

现场精确请求指定 WAN 网卡，但系统最佳路由快照选择 TUN。原接口目录仅给最佳路由接口填入 LUID，其余接口为零；精确请求的 GUID/LUID 因而无法匹配。目录身份完整性应独立于系统最佳路线。

对每个已枚举接口使用 ConvertInterfaceIndexToLuid 获取实际 LUID。转换失败仍保持未解析，不能猜测。精确路由查询优先传入已知 LUID，索引仍用于 IPv6 作用域。GetBestRoute2 的结果保留为 OS 事实；精确选择由完整目录归一化，实际发送合规另由执行器验证。

不添加业务配置、不改公共二进制模型，不删除稳定身份/源所有权检查，不更改系统路由。Windows 元数据回归检查目录中非最佳路线接口的真实 LUID；Aether 远端场景验证协议响应、实际源/接口/下一跳及策略清理。

本地 Networks Debug/Release 构建通过，各 212 项测试通过。远端 R2–R5 网卡身份匹配已通过，但 IPv6 TCP 尚未成功：WAN 8 和 WLAN 23 对 Google 两地址及阿里 IPv6 均超时；阿里 IPv4 TCP/TLS/DoH 通过。修复目录不等于修复 IPv6 发送。

R2 使用已知 LUID 时系统路由快照为 WAN 8，R3–R5 又选择 TUN 18；这些是 OS 查询事实，不能改写成指定出口成功。后续只在测试中比较“精确源/接口/下一跳”和“精确源/接口、系统下一跳”，定位 WFP 精确下一跳是否导致差异。该对照不是生产降级策略。

API 合同参考：[Microsoft GetBestRoute2](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-getbestroute2)。LUID 与索引描述请求接口；输出仍必须通过实际发送证据复核。

R7 在 WLAN 23 上比较精确网关与系统下一跳：Google 两个 IPv6 地址均在 TCP 阶段超时；阿里 IPv6 精确网关出现 10053，系统下一跳查询返回 1168。随后 IPv6 DoH 查询也返回 route-query-failed。IPv4 对照仍为六次成功。WinRM 元数据确认两张网卡均 Up，IPv6 默认路由 Alive，fe80::1 邻居 Reachable；这些元数据不能证明 IPv6 TCP 已可用。
