# DDNS Snap 对精确路由语义优化 RFC 的正式回复

> **状态**: SUBMITTED
>
> **回复方**: DDNS Snap
>
> **回复日期**: 2026-07-21
>
> **目标 RFC**: [精确路由语义优化 RFC](../ROUTING_SEMANTICS_OPTIMIZATION.md)
>
> **结论**: 有条件接受

## 一、总体意见

DDNS Snap接受RFC的上位语义、四种顶层路径模式、事件驱动闭环以及“请求意图不得冒充执行证据”的原则。

当前方案在以下条件满足后可以冻结：

1. `Direct`允许目标、源地址和接口分别使用显式、非空的选择策略；
2. `Automatic`与`Direct(... SystemSelected ...)`的区别由“是否禁止代理和登记适配器”明确界定；
3. `RouteAdapter`公开协议能力，不允许字节流适配器承载数据报请求；
4. 一发多收协议具有独立的响应基数和终止条件合同；
5. `ScopeId`只有一个权威归属，冲突时明确拒绝；
6. 精确路径证据区分实际观测、API绑定证明、推断和不可取得；
7. 入站Listener、NAT映射和专用源地址/端口池不进入本次出站路由合同；
8. 冻结后以一次不兼容升级同时迁移Runtime、DDNS Snap和Aether，不保留可空兼容层。

在RFC冻结前，DDNS Snap不接受依据草案提前修改Networks公共API。

## 二、DDNS Snap真实使用场景

DDNS Snap需要覆盖以下已有场景：

| 场景 | 必须表达的路径约束 | 必须取得的结果 |
| --- | --- | --- |
| 普通局域网单播扫描 | 系统选择源地址和接口 | 协议结果；路径证据允许不完整 |
| IPv6链路本地与组播扫描 | 固定接口；源地址可由该接口内选择 | 实际接口、有效ScopeId、多响应闭环 |
| IPv4广播与NBNS | 广播目标；接口可显式或系统选择 | 时间窗内0..N个响应 |
| 公网IPv4/IPv6地址守护 | 固定目标、源地址；接口可固定或由源地址解析 | 每个源地址独立的可达证据 |
| Clash/TUN环境下HTTP、DNS和DoH直连 | 固定传输目标、物理源地址和接口；保留逻辑Host/SNI | 证明未走代理或虚拟接口 |
| 伙伴服务器地址访问 | 配置服务器名保持逻辑身份；传输IP可变化 | 身份核对结果与实际传输路径分别返回 |
| Preferred IPv6源地址竞速 | 明确候选源地址集合 | 赢家、失败分支和实际路径证据 |
| IPv6恢复 | RS、DHCPv6 release/renew、网卡重启 | 动作结果与恢复后复检结果分离 |

这些场景相互独立，不要求属于同一轮次。单条结果完整后必须立即发布事件；慢请求不得阻塞其他请求完成。

## 三、对公开问题的逐项回复

### 1. `Direct`是否接受三个维度分别选择

**回复：接受。**

建议使用三个非空选择合同：

| 维度 | 允许策略 |
| --- | --- |
| 目标 | `RequestTarget`、`ExactAddress` |
| 源地址 | `SystemSelected`、`ExactAddress`、`PreferredSet` |
| 接口 | `SystemSelected`、`ExactInterface` |

`Direct`表示请求必须直连，不经过`SystemProxy`或`RouteAdapter`。只有标为`Exact*`的维度要求严格满足，但三个维度都必须显式填写选择策略。

如果拒绝逐维策略，Networks必须新增“受约束直连”顶层模式；DDNS Snap不接受删除上述真实能力。

### 2. `Automatic`是否允许请求自身携带固定IP

**回复：允许。**

请求自身的业务目标可以是域名或IP。`Automatic`不提供额外的传输目标覆盖，也不承诺特定源地址或接口。

需要明确以下区别：

- `Automatic`：采用端点规定的平台默认路径政策；
- `Direct(RequestTarget, SystemSelected, SystemSelected)`：目标仍来自请求，但明确禁止系统代理和登记路由适配器；
- `Direct(ExactAddress, ...)`：传输目标覆盖为指定IP，HTTP/DoH逻辑Host与TLS SNI仍保存在应用请求中。

因此两种模式不能仅根据“目标是否为IP”区分。

### 3. `RouteAdapter`是否扩展到数据报

**回复：接受带能力声明的统一适配器。**

适配器至少应声明：

- `ByteStream`；
- `Datagram`；
- 后续经独立RFC增加的专用能力。

端点必须在请求入队前检查能力。现有HTTP CONNECT类适配器只有`ByteStream`能力，不能用于UDP、DNS数据报、NBNS或组播。

如果数据报适配器的生命周期、NAT映射或多响应语义无法在本次RFC内冻结，应明确将其标记为未实现；不得把UDP静默转换成字节流。

### 4. 一发多收如何闭环

**回复：缺省采用时间窗闭环。**

建议请求显式声明响应策略：

- `FirstValidResponse`：首个满足过滤条件的响应结束请求；
- `CollectUntilWindowEnds`：时间窗内发布0..N个响应，窗口结束后发布完成；
- 持续监听不属于请求—响应端点，使用独立Listener/Stream合同。

IPv4广播、IPv6组播和NBNS发现缺省使用`CollectUntilWindowEnds`。所有响应携带同一个`RequestId`，同时具有独立响应序号和来源证据。

### 5. IPv6 `ScopeId`归属

**回复：`ExactInterface`是权威接口来源。**

目标地址携带的ScopeId只作为输入约束：

- 仅目标携带ScopeId时，可据此形成或验证接口选择；
- 同时提供`ExactInterface`时，两者必须一致；
- 不一致时在发送前拒绝；
- 不允许静默覆盖目标ScopeId或接口索引；
- 全局IPv6目标不得因为某次扫描接口而长期附带ScopeId。

最终请求内部只能存在一个规范化后的有效接口结论。

### 6. Preferred IPv6源地址竞速归属

**回复：属于源地址选择策略。**

`PreferredSet`描述调用方允许的源地址候选集合。一次集合竞速属于一次网络尝试内部的多个路径分支，不应分别消耗T1/T2/T3重试次数。

一次尝试应报告：

- 所有实际启动的候选；
- 每个候选的源地址、接口、开始时间、耗时和结果；
- 获胜候选；
- 未启动、取消或失败候选的原因；
- 所有候选失败后的聚合失败原因。

下一次重试可以重新竞速，但必须形成新的尝试记录。

### 7. 平台无法取得实际路径证据

**回复：按约束等级区分。**

- `Automatic`请求允许“协议成功但路径证据不完整”；
- 包含`Exact*`约束的请求，如果平台既不能实施也不能证明约束，应在发送前拒绝或最终失败；
- 底层API明确完成源地址或接口绑定，可以作为约束证明，不要求操作系统重复返回同一信息；
- 请求值本身不能作为执行证据。

建议引入非空证据来源枚举：

| `ProofKind` | 含义 | 可满足`Exact*` |
| --- | --- | --- |
| `Observed` | 从实际连接、响应或平台接口取得 | 是 |
| `ApiBinding` | 底层API已明确接受并执行绑定 | 是 |
| `Inferred` | 根据请求或环境推断 | 否 |
| `Unavailable` | 平台无法取得 | 否 |

证据还应区分`Requested`、`Resolved`和`Actual`，防止把请求意图写入实际路径字段。

### 8. PTR解析器与路径选择

**回复：解析对象与Resolver必须分开建模。**

PTR请求至少包含：

- 需要反查的IP；
- Resolver选择策略；
- Resolver传输目标；
- 源地址选择；
- 接口选择；
- UDP失败后的TCP回退政策。

`Automatic`可以明确委托系统Resolver；此时只承诺系统解析结果，不承诺精确Resolver路径证据。

`Direct`必须明确Resolver地址，并按源地址和接口约束发送原生DNS请求。TCP回退必须保持相同逻辑Resolver和路径约束，不能回退到系统DNS。

### 9. 恢复原语的平台范围

**回复：当前只承诺Windows实现。**

其他平台通过能力查询明确返回不支持。每个恢复原语必须分开报告：

1. 请求是否被接受；
2. 操作系统动作是否成功；
3. 系统地址是否发生预期变化；
4. 后续精确连通性复检是否成功。

命令退出码为0不能直接表示网络恢复；命令失败后原地址仍可达也不能反向标记该动作成功。

### 10. 入站Listener、NAT和专用端口池

**回复：另立RFC。**

本次路由RFC只定义出站请求路径。以下能力不得塞入`NetworkRouteDirective`：

- 入站监听地址和接口；
- Accept生命周期；
- UDP NAT映射与保活；
- 端口预留和复用；
- 专用源IP池的占有与释放；
- 长期Listener、持续流和服务器端会话。

### 11. 版本与迁移方式

**回复：采用V3/3.0并一次强制迁移。**

冻结后应：

1. 发布不兼容的Networks 3.0合同；
2. 删除`Route = null`、空地址、接口索引0等旧兼容表达；
3. 同步迁移Runtime、DDNS Snap和Aether；
4. 不提供旧类型别名、隐式转换或自动回退；
5. 完成三方真实程序运行验证后再发布正式包。

编译错误应作为遗漏迁移的发现机制。

## 四、路径证据的补充要求

DDNS Snap建议统一返回以下三层信息：

```text
RequestedPath
    调用方声明的顶层模式和逐维选择策略

ResolvedPath
    发送前解析得到的传输目标、源地址、接口或适配器

ActualPathEvidence
    本次尝试实际执行路径、ProofKind和证据完整度
```

建议结果至少提供：

- `PathConstraintStatus`：`Satisfied`、`NotSatisfied`、`NotProvable`、`NotApplicable`；
- 目标、源地址和接口各自的`ProofKind`；
- 代理或路由适配器实际标识；
- 未满足约束的固定错误码；
- 每次尝试独立的路径证据；
- 协议成功与路径约束成功两个独立结论。

只有协议成功且所有`Exact*`约束均为`Satisfied`时，结果才能称为“精确路径成功”。

## 五、事件与时序意见

DDNS Snap确认采用松散数据和事件驱动模型：

- 单条完整结果到达后立即发布，不等待同批其他目标；
- 多个请求不形成隐式事务轮次；
- 新数据允许覆盖尚未消费的旧数据；
- 重复请求和重复响应不得破坏请求自身闭环；
- 慢请求不得延迟其他请求的成功或失败事件；
- 批量API只优化入队和读取，不改变逐请求独立完成。

该语义适用于网络端点，不要求DDNS设备树、发布快照或UI采用Networks内部队列结构。

## 六、冻结前置条件

DDNS Snap在以下事项完成前维持“有条件接受”：

- [ ] 第三节11项问题形成最终决议；
- [ ] 每个端点完成路径模式与能力矩阵；
- [ ] `Direct`逐维选择合同定稿；
- [ ] 路径证据类型和`ProofKind`定稿；
- [ ] IPv6 ScopeId规范化规则定稿；
- [ ] 一发多收合同定稿；
- [ ] PTR Resolver模型定稿；
- [ ] Windows恢复原语的分步结果合同定稿；
- [ ] Runtime与Aether提交正式回复；
- [ ] 三方迁移清单通过评审。

满足上述条件后，DDNS Snap同意将RFC状态提升为`ACCEPTED`并进入Networks 3.0实施阶段。
