## 已提交的正式回复

- [DDNS Snap正式回复](rfc-responses/DDNS_SNAP_ROUTING_SEMANTICS_RESPONSE.md)：有条件接受，逐项回复11个公开问题。

DDNS Snap对原路由RFC有条件接受；Aether已进一步确认总体规划覆盖其需求并原则接受进入合同冻结阶段。双方均确认：
四种顶层模式只是路径提供者，不能代替完整精确访问控制；`Direct`必须允许
目标、源地址和接口分别选择。新增的总体规划继续覆盖接口、下一跳/网关、本地端口、路由作用域、IP层政策和协议专属
Resolver等维度。本文的11项问题只有在总体规划的选择器、能力矩阵和证据合同冻结后才能关闭。

本文用于公开征求Runtime、DDNS Snap、Aether及其他消费者意见。当前确认的问题是`Route = null`语义不明确；
当前尚未确认的是四种顶层模式的字段约束、各协议能力边界及实际路径证据的表示方式。任何未列入覆盖矩阵的场景都不能
因为“可以勉强映射”而被视为已经支持。

评审结论只允许以下三种：

- **接受**：场景、字段合法性、失败语义和证据均明确；
- **有条件接受**：需要补充能力声明或协议专用合同；
- **不覆盖**：明确列入非目标或必须新增模式，不能静默退回`Automatic`。

## 一、上位语义

1. 网络访问对象、逻辑身份和传输路径是三个不同概念，不得互相推断。
2. 逻辑身份由调用方提供并保持稳定；目标IP、源IP、接口索引和ScopeId只是一次网络访问的可变路径信息。
3. 网络数据是松散事实。公共库只保证单条请求及其响应完整闭环，不建立跨请求、跨伙伴或跨轮次的事务依赖。
4. 接收是事件驱动的。完整响应到达后必须立即发布事件，不等待同批其他请求完成。
5. 重复请求、迟到请求和新数据覆盖旧数据是上层允许的运行形态。公共库按`RequestId`闭环，不替业务层建立全局轮次。
6. 路由证据必须来自实际执行结果。不得用配置意图、系统默认路由或传输对端地址冒充已验证路径。

## 二、身份与名称解析边界

### 2.0 GUID绝对跟踪

- 对外所有请求、响应、失败、取消、完成和迟到响应统一使用非空`Guid RequestId`绝对跟踪。
- Pending、匹配、重试、完成选择、移除和等待只允许使用`RequestId`。
- 便捷工厂可以在构造请求前同步生成GUID；低层`Send`/`TrySend`收到`Guid.Empty`必须在入队前拒绝，禁止异步换号。
- `TKey`仅为允许重复的用户查询数据，不能成为第二套内部身份。
- Attempt、PreferredSet竞速分支和多响应观测也使用`Guid`，通过`AttemptId`、`BranchId`、`ResponseId`显式关联到根`RequestId`。
- 每个Attempt至少创建一个唯一`BranchId`，普通请求也不例外；每条`ResponseId`直接归属于`BranchId`，形成固定
  `RequestId → AttemptId → BranchId → ResponseId`父链。
- 完整层级和生成规则以[精确网络访问控制总体规划](PRECISION_NETWORK_ACCESS_CONTROL_MODEL.md)第二节为准。

### 2.1 正确关系

```text
调用方逻辑身份（例如配置服务器名）
    -> 名称/地址守护程序发布当前候选IP
    -> 一次请求选择目标IP、源IP和接口
    -> 响应报告实际目标IP、源IP和接口
```

- 一个逻辑身份允许同时对应多个IPv4、IPv6和带ScopeId的链路本地地址。
- 地址守护程序只更新候选传输地址，不改变逻辑身份。
- 接收端看到的`RemoteEndPoint`只能作为诊断证据，不能作为伙伴、会话或业务记录的主键。
- 公共库的`TKey`是调用方查询键；它不是内部请求身份，也不是传输地址主键。
- 公共库继续只按`RequestId`匹配、完成、重试和移除请求。

### 2.2 需要审计

- [ ] 搜索所有以远端IP、URL、ScopeId或本地选路结果作为长期身份键的实现。
- [ ] 确认名称解析刷新只替换候选地址，不复制逻辑对象。
- [ ] 确认同一逻辑身份通过不同地址到达时仍落入同一上层记录。
- [ ] 响应快照同时保留调用方逻辑键和实际传输证据，但二者不得互相覆盖。

## 三、移除可空路由的模糊语义

当前`NetworkRouteDirective? Route = null`同时承担兼容入口和“让系统自动选择”的含义。候选方案在下一次不兼容升级中
移除可空路由，要求调用方显式选择路径模式。

建议保留并收紧以下模式：

| 模式 | 明确含义 | 失败时是否回退 |
| --- | --- | --- |
| `Automatic` | 明确授权操作系统选择目标解析、源地址和接口 | 不转换成其他模式 |
| `Direct` | 使用直连路径；目标、源地址和接口的选择策略必须逐项显式 | 不回退到系统代理或路由适配器 |
| `RouteAdapter` | 使用已登记且能力匹配的路由适配器 | 不回退到直连或系统代理 |
| `SystemProxy` | 明确授权使用系统代理 | 不冒充物理直连证据 |

实施清单：

- [ ] 请求合同中的`Route`改为非空值类型；`default(NetworkRouteDirective)`必须是非法的`Unspecified = 0`，发送时明确拒绝。
- [ ] 提供显式工厂，如`Automatic()`、`Direct(...)`、`ViaAdapter(...)`、`SystemProxy()`。
- [ ] 删除把`null`自动解释为系统选路的兼容重载。
- [ ] 每种模式建立字段合法性矩阵，非法组合在发送过滤阶段明确拒绝。
- [ ] 不允许省略`Route`的构造函数或重载；编译错误用于强制消费者迁移。
- [ ] `Direct`声明精确源地址或精确接口后，实际无法满足必须失败，禁止静默降级。
- [ ] `Automatic`结果只证明系统路径成功，不证明任何指定物理网卡或指定源地址成功。
- [ ] `TargetAddress`缺省的语义按协议单独定义；不能同时表示“尚未解析”和“允许系统解析”。

### 3.1 `Direct`不能只定义为“三项全部固定”

源码消费者已经存在以下有效需求：

- DDNS Snap链路本地IPv6和组播扫描固定目标与接口，但允许系统在该接口上选择源地址；
- DDNS Snap公网IPv6连通性检测固定目标与源地址，接口索引有时可获得、有时只能由系统解析；
- Aether DoH/HTTP评分固定连接目标IP，但允许系统选择源地址与接口；
- Aether可从多个Preferred IPv6源地址中竞速，而不是预先固定唯一源地址。

因此，RFC不接受用空地址、`0`或省略标志继续表达“由系统选择”。候选做法是让`Direct`的三个维度各自使用非空选择策略：

| 维度 | 候选策略 | 含义 |
| --- | --- | --- |
| 目标 | `RequestTarget` / `ExactAddress` | 使用请求本身目标，或固定传输目标IP |
| 源地址 | `SystemSelected` / `ExactAddress` / `PreferredSet` | 系统选择、固定源地址或在明确候选集中选择 |
| 接口 | `SystemSelected` / `ExactInterface` | 系统选择或固定接口索引 |

`Direct`仍然表示不经过系统代理或登记适配器，并且不得切换顶层模式；其中标为`Exact*`的维度必须严格满足。
如果评审决定`Direct`必须强制三项全部精确，则必须新增另一种“受约束直连”模式承载上述真实场景，不能删除这些能力。

### 3.2 应从路由指令移出的字段

- `PreserveHostAndSni`属于应用请求的逻辑服务身份，不属于网络路径；它应随HTTP/DoH请求保存。
- 重试次数、超时和Preferred源地址竞速策略属于请求/尝试策略；不能用路由模式暗示。
- 广播、组播、单播和响应数量属于协议请求合同；不能用路由模式推断。

## 四、请求意图与实际路径证据分离

新增统一的只读路径证据，至少包含：

- 请求的路径模式；
- 请求目标与实际目标；
- 请求源地址与实际源地址；
- 请求接口与实际接口；
- 是否使用路由适配器或系统代理；
- 路径是否完整满足请求约束；
- 本次尝试编号、耗时和底层错误。

实施清单：

- [ ] TCP、UDP、Ping、HTTP、DoH、PTR和NBNS使用同构证据字段。
- [ ] 精确路由成功必须同时报告实际源地址和接口，缺证据不能标为精确成功。
- [ ] 响应中的实际路径只描述本次尝试，不回写或改变调用方逻辑身份。
- [ ] 每次重试分别保存路径证据，不能只保留最后一次。
- [ ] 系统自动路径与显式物理路径在类型或枚举上可直接区分，不依赖空值推断。

实际证据允许“平台无法取得”，但必须明确表示不可用，不能以`0`、空地址或请求值冒充实测值。评审需在
`HasActualSourceAddress`/`HasActualInterface`标志、可选值类型或分类型证据之间选定一种。成功只表示协议请求成功；
只有证据完整且满足全部`Exact*`约束时，才能同时标记为精确路径成功。

## 五、端点与路径模式能力矩阵

顶层模式不代表每种协议都能实现。端点必须公开能力，并在入队前拒绝不支持的组合。

| 端点/协议 | `Automatic` | `Direct` | `RouteAdapter` | `SystemProxy` | 说明 |
| --- | --- | --- | --- | --- | --- |
| TCP Connect | 支持 | 支持 | 有条件支持 | 不适用 | 适配器必须具有字节流能力；系统代理不是裸TCP通用语义 |
| UDP Datagram | 支持 | 支持 | 待定义 | 不适用 | 现有字节流适配器不能承载UDP；需数据报适配器能力或明确不支持 |
| IPv4/IPv6 Ping | 支持 | 支持 | 不支持 | 不支持 | ICMP不能经现有HTTP CONNECT适配器或系统代理 |
| HTTP/DoH | 支持 | 支持 | 支持 | 支持 | 逻辑Host/SNI与传输目标必须分离 |
| DNS PTR | 支持 | 支持 | 待定义 | 不适用 | 当前是原生DNS UDP并支持TCP回退；需明确系统DNS地址选择与精确解析器路径 |
| NetBIOS | 支持 | 支持 | 待定义 | 不适用 | 广播/多响应与逐请求闭环需另行确认 |
| RS/DHCPv6/网卡重启 | 不适用 | 不适用 | 不适用 | 不适用 | 它们是恢复原语，不是请求路由模式 |

`RouteAdapter`必须声明传输能力，例如`ByteStream`、`Datagram`或将来的专用能力；仅凭整数ID不能证明它能承载当前协议。

## 六、使用场景覆盖审计

| 使用场景 | 候选映射 | 当前判断 | 仍需确认 |
| --- | --- | --- | --- |
| 普通域名/URL访问，允许系统解析和选路 | `Automatic` | 覆盖 | 返回哪些实际路径证据受平台限制 |
| 普通IP单播，允许系统选择源和接口 | `Automatic`或`Direct(RequestTarget, SystemSelected, SystemSelected)` | 有条件覆盖 | 两种表达必须只保留一种权威语义 |
| 固定目标、源地址和接口的物理访问 | `Direct(Exact, Exact, Exact)` | 覆盖 | 无法绑定时必须失败 |
| 固定目标IP，系统选择源和接口 | `Direct(Exact, SystemSelected, SystemSelected)` | 覆盖 | 需接受3.1的逐维策略 |
| 固定接口，系统在接口内选择源地址 | `Direct(RequestTarget, SystemSelected, ExactInterface)` | 覆盖 | 需接受3.1的逐维策略 |
| IPv6链路本地地址及ScopeId | `Direct` + 精确接口 | 有条件覆盖 | ScopeId归目标还是接口策略必须唯一化 |
| IPv4广播、IPv6组播和一发多收 | `Automatic`或`Direct` | 有条件覆盖 | 路由可表达，但响应基数与终止条件不是本RFC已解决问题 |
| Preferred IPv6源地址竞速 | `Direct(..., PreferredSet, ...)` | 有条件覆盖 | 候选集来源、竞速证据和失败聚合待定义 |
| 系统代理HTTP/DoH | `SystemProxy` | 覆盖 | 只能证明系统代理访问成功，不证明代理出口物理路径 |
| 显式HTTP CONNECT/SOCKS路径 | `RouteAdapter` | 覆盖字节流 | SOCKS及能力声明尚需实现/验证 |
| UDP经代理、UDP NAT或专用源IP池 | 数据报`RouteAdapter`或独立转发层 | 未完整覆盖 | 需决定适配器是否扩展到数据报；RequestId只做外部跟踪，不等于NAT键 |
| 为转换程序保留专用本地IPv4/IPv6地址 | `Direct`使用指定源地址 | 部分覆盖 | 地址独占、端口保留和虚拟接口属于操作系统资源管理，不由路由指令保证 |
| 入站监听、服务端接受连接 | 独立Listener合同 | 不覆盖 | 本RFC只定义出站请求路径，不应套用请求路由模式 |
| 自动失败后改走代理或原计划外接口 | 上层显式发起新请求 | 覆盖 | 重试不能改变冻结计划；可在原PreferredSet内重新选择 |
| RS、DHCPv6更新、网卡重启 | 公共恢复原语 | 有条件覆盖 | Windows权限、平台能力和分步证据待定义 |

结论：**四种顶层模式覆盖主要出站路径类别，但当前草案不能宣称满足全部使用场景。** 至少数据报适配器、
`Direct`逐维选择策略、广播/组播多响应、PTR解析器选路、实际证据不可用的表示和入站Listener边界必须先形成明确结论。

## 七、公开征求意见

请消费者按“场景—期望路径—失败语义—必须返回的证据”四项回答，不接受只回复“兼容”或“可用”。

1. `Direct`是否接受目标、源地址、接口各自显式选择`SystemSelected`或`Exact*`？如果不接受，新的受约束直连模式叫什么？
2. `Automatic`是否只表示三个维度都由系统选择，还是允许请求本身已经携带固定IP目标？
3. `RouteAdapter`是否扩展为带能力声明的通用适配器，支持字节流和数据报；还是只保留字节流并另建UDP转发合同？
4. IPv4广播、IPv6组播和NBNS的一发多收，按首个有效响应闭环、时间窗闭环，还是返回持续流？
5. IPv6 `ScopeId`是否只由`ExactInterface`派生，禁止目标地址和接口策略各存一份可能冲突的值？
6. Preferred IPv6源地址竞速属于`SourceSelection.PreferredSet`，还是独立的尝试策略？每次竞速失败如何进入尝试历史？
7. 实际源地址或接口无法从平台可靠取得时，结果应标记“协议成功但证据不完整”，还是整个精确请求失败？
8. PTR已使用原生DNS数据报并支持TCP回退；`Automatic`应如何选择系统DNS地址，`Direct`又应如何同时约束解析器、源地址和接口？
9. RS、DHCPv6 release/renew和网卡重启是否只承诺Windows实现，并通过能力查询在其他平台明确拒绝？
10. 入站Listener、NAT映射和专用源IP/端口池是否另立RFC，避免扩大本次出站路由合同？
11. 下一版是否命名为V3/3.0，并一次性强制迁移DDNS Snap、Aether和Runtime，完全不保留可空兼容层？

## 八、事件驱动与松散数据

公共库只保证单请求闭环：

```text
请求进入 -> 一次或多次尝试 -> 首个有效成功或最终失败 -> 立即发布事件
```

公共库不得增加以下隐含屏障：

- 等待同一批其他请求完成后再发布；
- 等待多个服务器或多个地址形成一致轮次；
- 用定时轮询代替已有的完成事件；
- 因旧数据可能重复而延迟新数据；
- 把业务层的“发布快照”解释成网络层事务提交。

实施清单：

- [ ] 成功、最终失败、迟到响应和重试事件均在状态转换完成后立即异步派发。
- [ ] 批量API只是批量入队/读取优化，不改变每条请求独立完成的语义。
- [ ] 验证慢请求不阻塞其他请求的完成事件。
- [ ] 验证同一业务键的多个请求可以并存，仍只按各自`RequestId`闭环。

## 九、连通性证据与恢复动作边界

Networks负责提供精确测试和可验证的恢复动作原语，不负责决定DDNS业务何时重置网卡。

### 9.1 证据分类

- `Automatic`探测：只回答系统当前自动路径是否成功。
- 显式`Direct`探测：回答请求声明的目标、源地址和接口选择约束是否全部满足。
- 邻居缓存、ARP、NUD：是独立的本地观测证据，不等同于ICMP结果。
- 代理或路由适配器成功：只证明该适配路径可用，不证明物理直连可用。

### 9.2 恢复原语

- [ ] 提供明确的RS发送结果，报告实际接口和系统错误。
- [ ] 提供DHCPv6 release、等待、renew的分步结果，不把命令成功伪装成地址恢复成功。
- [ ] 提供网卡重启结果和重启后的地址快照证据。
- [ ] 恢复动作本身与恢复后连通性复检分开建模。
- [ ] 所有动作允许调用方配置等待时间和取消令牌，不在库内硬编码业务周期。
- [ ] 权限不足、命令拒绝、命令成功但网络未恢复必须是不同结果。

DDNS地址守护程序的业务顺序仍由DDNS项目定义，例如：逐源检测、全部失败后RS、复检、DHCPv6更新、复检、最后重启网卡。该顺序不进入公共端点基类。

## 十、健康与业务数据边界

- 公共库不定义“心跳决定在线”的业务语义。
- 一次身份查询、一次大数据推拉和一次连接探测都是独立网络请求，各自发布结果。
- 调用方可以把任何成功通信作为附带健康信息，但健康字段不得反向阻止业务数据接收、合并或发布。
- 大数据本来需要传输时，不得为了所谓健康检查把它替换成另一套影响业务判断的协议。

## 十一、迁移与验证顺序

1. [ ] 收集Runtime、DDNS Snap、Aether及独立消费者意见，关闭第七节全部问题。
2. [ ] 冻结上述语义、端点能力和字段合法性矩阵。
3. [ ] 新建不兼容请求合同，移除`Route = null`。
4. [ ] 逐端点实现统一路径证据，不保留新旧语义混用。
5. [ ] 为Automatic、Direct、RouteAdapter、SystemProxy分别建立成功与失败测试。
6. [ ] 在存在Clash/TUN的机器上真实验证显式物理IPv4/IPv6路径。
7. [ ] 验证同一目标在自动路径成功、显式物理路径失败时能给出两个独立结论。
8. [ ] 验证同一逻辑键经多个IPv4/IPv6/ScopeId访问，不产生新的网络层身份。

## 十二、非目标

- 不在Networks中实现DDNS伙伴身份表、设备合并、UI刷新或发布快照。
- 不要求不同请求属于同一轮次，也不承诺只接收一次。
- 不通过传输源IP推断业务对象。
- 不把操作系统默认路径结果当作显式物理路由证据。
- 不为兼容旧调用继续保留含义不清的空值路由。
