# 安全审计答复报告

> 状态说明：本文记录整改过程和历史验收清单。1.0.19 已完成统一打包；当前已验证能力和仍待宿主实机验证项目以 WEBVIEW2_RELEASE_STATUS.md 为准。

## 1. 答复范围

本报告答复《安全审计报告》中提出的 WebView2 生命周期、资源清理、状态一致性和公共接口问题，并同步纳入 Runtime 无配置文件化、CLI 单点控制、反射路由和安全退出整改。

本文所称“安全”仅指业务逻辑安全：避免重复任务、资源泄漏、状态误报、内存对象残留和宿主退出闭环，不涉及网络攻击模型。

## 1.1 整改所有权答复

最终整改由 Runtime 仓库统一落实。WebView2 使用方和其他宿主侧以后只提交问题、证据、复现步骤和审查意见，不再直接修改 Runtime/WebView2 公共库源码。

原因是前期变更量过大，多个位置同时修改会造成协议、生命周期、CLI catalog、文档和发布 DLL 不一致。整改期间执行变更冻结：

- Runtime 侧负责设计决议、源码修改、测试、文档和发布；
- WebView2 使用方负责复现、验收和提出意见；
- 宿主只做公开接口接入和删除临时兼容代码；
- 未经 Runtime 侧合并验证，不再接受另一边直接落入公共库的实现改动。

完整实施计划见同目录《完整整改方案.md》。

## 2. 总体处理决策

- 接受审计报告列出的三项高风险问题和四项中风险问题。
- WebView2 生命周期统一由 Host 管理，CommandTarget 不再绕过 Host 直接初始化或停止 Registry。
- Ambient 输入改为可重复启动、停止并可报告 Faulted 的单一状态机。
- Program 初始化失败必须反向回滚；停止失败必须继续清理其余 Program。
- 接受已批准的一次性破坏性迁移，不恢复旧 `IWebRuntimeControl`，统一使用新会话、Program 和 Frame 架构。
- Runtime 取消 `diagnostic-switchboard.json`，源码固定身份，命令行参数提供唯一启动期覆盖。
- 所有整改通过真实 CLI 与安全退出测试后再发布。

## 3. WebView2 审计问题答复

### 3.1 Ambient 停止后无法重启

答复：确认缺陷。

处理：删除 `_started/_stopped` 双标志组合，使用 `Stopped / Starting / Running / Stopping / Faulted / Disposed` 状态机。每次启动创建新的 CTS、鼠标任务和键盘任务；停止完成后允许再次启动。

验收：连续执行 `Start -> Stop -> Start -> Stop`，每次实际任务和报告状态一致。

### 3.2 Program 初始化部分失败造成资源泄漏

答复：确认缺陷。

处理：记录成功初始化顺序；后续初始化失败时按反向顺序调用 Stop；每项回滚独立捕获异常，最终汇总错误并把 Host 设置为 Faulted。

验收：A、B 初始化成功、C 失败后，B、A 均收到停止调用，Registry 和活动执行表为空。

### 3.3 单个 Program 停止失败阻断整体退出

答复：确认缺陷。

处理：停止流程改为“全部尝试、最后汇总”。单项失败不能阻断后续 Program、执行取消、登记撤销和 Host 状态更新。

验收：B 停止抛错时，C 仍完成停止，最终状态为 `StoppedWithErrors`，不存在活动登记。

### 3.4 生命周期绕过统一锁

答复：确认缺陷。

处理：CommandTarget 的 initialize/stop 统一调用 WebRuntimeProgramHost；Registry 的直接生命周期方法收紧为内部实现。

验收：CLI 初始化、CLI 停止、宿主启动和宿主退出并发时只形成一条串行状态链。

### 3.5 重复释放不安全

答复：确认缺陷。

处理：所有异步资源拥有者增加原子 disposed 状态；重复 Dispose 直接返回；Dispose 后启动和执行返回明确错误。

验收：重复 Stop、重复 Dispose 均不抛异常、不重复释放资源。

### 3.6 后台输入异常但状态仍显示运行

答复：确认缺陷。

处理：鼠标和键盘任务分别记录状态和最后错误；pulse 异常把控制器转为 Faulted，并通过 Runtime 监视点发布。

验收：注入 pulse 异常后任务终止、状态为 Faulted、错误可查询且可按策略重新启动。

### 3.7 公共接口破坏性变更

答复：接受已批准的一次性破坏性迁移。

处理：不恢复 `IWebRuntimeControl`。会话能力统一使用 `IWebRuntimeSession`，业务执行统一使用 `IWebRuntimeBusinessProgram` 与 Program Host/Registry，线协议统一使用 `RuntimeDiagnosticFrame`。

验收：活动源码不存在旧接口、旧 Envelope、旧 DTO 或旧管道入口；新架构消费方编译通过，迁移文档提供旧能力到新接口的对应关系。

## 4. Runtime 配置与四端点答复

### 4.1 取消运行时 JSON 配置

答复：接受。

`diagnostic-switchboard.json` 容易因相对路径、旧目录、复制文件和多进程目录混用而产生错误覆盖，因此不再读取、合并或写回。

最终规则：

```text
源码声明 = 固定可靠基线
启动参数 = 唯一临时覆盖入口
CLI 指令 = 当前进程内存状态
```

主管道使用 `--diag-pipe` 覆盖源码声明；主记录文件使用 `--diag-file` 覆盖源码声明。进程重启后恢复源码默认值。

### 4.2 四条独立主管道

答复：已证明强制独立端点方向正确。

整改后四个宿主不再从 JSON 读取管道名，旧 JSON 无法使 Service、Agent、UI 和 Agent UI 回落并争抢同名管道。

验收：四端同时运行，四条主管道分别完成 `host.info` 和生命周期查询。

## 5. CLI 缺口答复

### 5.1 动态 watch point 单点开关

答复：确认标准 catalog 缺口。

新增：

```text
switchboard.point.list
switchboard.point.enable <id>
switchboard.point.disable <id>
```

不存在的 ID 返回 `OUTPUT_POINT_NOT_FOUND`。发布条件必须同时满足 Global、Section、Point 和输出通道启用。

### 5.2 reflection.get 路由

答复：确认需要修复。

目标参数改为实际 Hub 注册目标的路由模板，不再固定指向不存在的 `diagnostics.reflection`；位置参数和命名参数分别回归。

## 6. 安全退出答复

### 6.1 shutdown-watch 等待自身

答复：确认退出闭环。

shutdown-watch 属于退出协调基础设施，不得参与业务 `CanExit` 门槛。它负责等待其他登记清空，随后自行销户并退出。

验收：pending 清单只包含尚未结束的业务单元；其他单元清空后 Service 正常返回退出码 0；超时返回约定超时码。

3. 修复 shutdown-watch 自等待闭环；
4. 补齐 point 级 CLI 和 reflection.get；
5. 重构 WebView2 Host 生命周期；
6. 完成初始化回滚与可靠停止；
7. 重构 Ambient 输入状态机；
8. 清理旧接口残留并补充迁移对照；
9. 完成 Debug/Release、异常路径、真实四端 CLI 和安全退出测试；
10. 全部通过后重新发布。

### 9.4 四宿主强制写 JSON 的定位

四个主程序在 Runtime Monitor 启动前强制写入各自管道名，已经证明四端点身份固定方案有效，但该实现仅作为过渡兼容措施。

完成 Runtime 无配置文件化后必须删除四个宿主中的强制写 JSON 逻辑，最终只保留：

```text
源码声明固定管道身份
--diag-pipe 临时覆盖
Runtime 不读取或写入 diagnostic-switchboard.json
```

不得把宿主强制写 JSON 固化为长期标准，否则配置文件路径和旧值问题仍然存在，只是由读取覆盖变成启动时覆盖。
