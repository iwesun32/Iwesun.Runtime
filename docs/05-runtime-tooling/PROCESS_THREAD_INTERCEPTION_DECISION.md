# 进程/线程拦截方案决策（讨论纪要）

> **状态**: CURRENT | **最后更新**: 2026-07-09
> **性质**: 设计讨论结论（放行版）

## 背景

本轮讨论目标是确认：

1. 是否采用“直接继承系统类并改写”的主路线；
2. 如何在尽量少改业务源码的前提下，给外部业务程序提供通用监控调试能力（DLL 接入）；
3. 先给出放行方案与路线图，再进入共享内存专题讨论。

## 双方核心观点归纳

### 观点 A：希望通过继承系统类来截获逻辑

- 优点：语义接近系统类型（`Thread` / `Task` / `Process`），业务理解成本低。
- 目标：在自定义类型中增加登记、状态、管控接口，尽量不改变业务使用方式。

### 观点 B：继承不是全链路拦截手段

- .NET 大量系统路径为静态入口、非虚方法或框架内部构造，无法保证必经子类逻辑。
- 即使继承可行，也只能覆盖“显式走到自定义类型”的调用路径。
- 若目标是稳定落地，必须有“可控入口”而不是依赖运行时穿透。

## 达成结论（放行）

### 结论 1：继承可作为语义外壳，但不作为主拦截机制

放行意见：**继承可保留，主机制必须是包装/统一入口。**

- 允许保留与系统类接近的前缀类型（如 `RThread`、`RTask`、`RProcess`）。
- 不假设系统会自动穿过自定义改写路径。
- 拦截边界定义为：**业务创建入口**。

### 结论 2：以“最小改动创建点替换”为首阶段策略

- 以工厂/包装入口替换业务创建点（线程、任务、进程）。
- 保持业务逻辑本体不变，先控制“创建、等待、停止、退出”关键点。
- 允许后续用自动化工具（Analyzer/CodeFix）降低人工改造成本。

### 结论 3：受管与观察分层

进程/线程/任务按 ownership 分类：

- `InternalManaged`：框架创建并受控，支持完整生命周期管理。
- `ExternalObserved`：系统或外部创建，仅统计与观察，不主动干预其退出。

## 技术方案（放行版）

### 1. 架构骨干

- **Managed Registry（进程内主账本）**：线程安全、强一致，记录登记与状态流转。
- **Control Plane（监控指令面）**：支持 `init/stop/wait/snapshot` 等基础命令。
- **Adapter API（业务接入面）**：对业务暴露最小接口，屏蔽内部实现细节。

### 2. 状态与生命周期

统一状态模型按“创建→运行→等待/收尾→完成/取消/故障”闭环推进。

- 必须有状态跃迁约束，避免乱序状态写入。
- 未登记对象只进入观察视图，不进入受管退出编排。

### 3. 退出编排

遵循统一顺序：

1. 通知停止；
2. 唤醒阻塞；
3. 准备与清理；
4. 完成退出（超时进入兜底路径）。

## 路线图

### Phase 1（当前放行）

- 固化“创建点替换 + 包装对象 + 受管登记”主路径。
- 先覆盖常用入口：线程创建、任务创建、进程启动与等待。
- 建立 `InternalManaged / ExternalObserved` 分类视图。

### Phase 2

- 补齐指令面幂等与权限边界。
- 引入批量改造工具（Analyzer + CodeFix），减少业务人工改造。
- 扩展更多系统调用模式的兼容封装。

### Phase 3（共享内存专题）

- 评估跨进程共享状态副本：`MemoryMappedFile` + 版本化协议。
- 先做观测副本，再评估是否承担主账本职责。
- 重点验证一致性、恢复能力和性能收益。

- 共享内存数据结构与并发协议在下一轮专题中单独讨论。
